## 2. What blocked self-hosting, and the fixes

The previous attempt (2026-10-02, project `gittifacts-raw`) stalled with the O5 proposal failing as "the
workspace is still starting" and the bootstrap CI hanging. The platform problems, in the order they bit:

1. **Forks of a large repo can't be cloned (P0, fixed in `2d092c7`, deployed 05:59).** Artifacts' upload-pack
   answers HTTP 500 to any bulk fetch from a *fork* of this repo (full, `--depth=1`, `--filter=blob:none`),
   while `ls-refs`, incremental fetches and every fetch from the main repo work. The same 18 MB history pushed
   into a fork of a small repo clones in 2.7 s, so the content is fine: a fork can't serve the objects it
   inherited. CI checkouts, workspaces and agents all clone forks. Fix: `ArtifactsGitHost.forkRepo` pushes the
   default branch's full history into every new fork once (`refs/gittifacts/fork-objects`, `haves: []`).
   Cost: `start_change` takes 15.7 s on this repo (fork + 18 MB copy). Verified live: the system proposal's
   fork carries the ref and a blobless shallow fetch from it takes 1.1 s.
2. **Chunked pushes (P1, documented).** Artifacts' receive-pack refuses chunked request bodies: any push over
   git's default 1 MiB `http.postBuffer` fails with HTTP 400, "the remote end hung up unexpectedly". The import
   grant's `command` and the migrate guide now pass `-c http.postBuffer=524288000`; the git guides got the same
   (dogfood change E).
3. **A repo whose detected pipeline is red can never adopt one (P0, fixed in `482a744`, deployed 06:25).** CI
   came from the base only, so the Change adding `.platform/ci.ts` was judged by the red defaults, a failing
   Change can't be reviewed, and the queue judges from base too: deadlock. Now, while the base has no
   `.platform/ci.ts`, a Change that adds one is judged by it. Safe because every `.platform/` change is Lane 2
   with a non-author human approval (hard-coded `policy.changed`). Verified live: the adopting Change's
   `plan-ci` read `source: "file"` from its head.
4. **Evidence step logs unreadable (P2, fixed through the platform, change G).** `GET /api/v1/blobs/:ref`
   refused the `:` in `ci-logs/<run>/evidence:red-green.log`.
5. **Queue replays never had their blobs (P0 for any busy repo, fixed in `f67b03b`).** The first landing onto a
   moved main (E merged while A and G were landing) needs a replay in the queue's scratch repo. The job fetched
   its inputs with the checkout's `blob:none` filter, swallowed errors, and `merge-attempt` (lazy fetching off)
   died on the first changed blob. Reproduced against the live scratch repo; now `--no-filter --depth=1`.
6. **A dropped build stalled the queue for 90 minutes (P1, fixed in `a4bf134`).** After 6 failed attempts the
   shell drops `BuildBatchTree` and the batch stayed `building` until the 90-minute CI run timeout, holding
   every landing behind it. New `buildTimeoutMs` (15 min).

## 6. What CI on this monorepo costs

Container time is from each run's `usage` (`ci-runs/<run>/summary.json`); runs a newer push superseded have no
summary and are left out. Instances are `standard-2`.

|---|---|---|---|
| Bootstrap on main (detected defaults, red) | 7.9 min | 7.1 | 7 |
| System `.platform/*` proposal (defaults, red) | 23.1 min | 25.5 | 12 |
| Adoption Change, green push (`eb99ce8`) | 21.7 min | 44.5 | 11 |
| A Change on the adopted pipeline (A, E, G; first runs of B, D, F) | 19–33 min | 41–83 | 10–12 |
| A queue batch or landing (user steps only, no evidence) | 6–17.5 min | 8.3–10.3 | 5–6 |
| GitHub deploy gate (typecheck + platform suite, `ubuntu-latest`) | 7.2–7.7 min | n/a | 1 runner |

**Totals for the day** (22 runs with a summary): **774 container-minutes, about 13 container-hours** (13
Change and bootstrap runs: 686; 9 queue runs: 89), plus about 23 GitHub Actions minutes for three deploy gates.
Seven Changes merged, so roughly 110 container-minutes per merged Change, a third of it spent on re-runs (two
classifier flakes, two requested changes, the adoption Change's three pushes).

Where the time goes on a Change: user steps take 5–6 min when the install is cached (assets 0.5–6 min,
typecheck ~4 min, unit 1 min, docs 20 s); **evidence takes 13–17 min**, because red/green, test-run and
coverage each run the whole suite at the root (2,575 tests), red/green twice on base. Under six concurrent
Changes it stopped finishing at all (vitest's 1,200 s limit). The merge queue skips evidence, so a landing costs
about a fifth of a Change. Compared with the GitHub gate (7.5 min for typecheck plus the platform suite), the
platform runs more checks per push but spends 3–4× the wall time, almost all of it in evidence.

## 7. Workflow until cut-over

GitHub stays canonical (DECISIONS 2026-10-03). A dogfooded change is planned, pushed, gated, reviewed and merged
on gittifacts, then cherry-picked to GitHub main (`git cherry-pick -x` plus a `Gittifacts-Change: <id>` trailer)
and deployed by the usual gate. Fixes the platform needs before it can gate anything (here: fork copies,
pipeline adoption, the two queue fixes) land on GitHub first and reach the mirror with a sync Change, which
replays the GitHub-only commits onto the mirror's main. That sync is manual for now, so the mirror trails GitHub
between syncs (today: by the four platform fixes and the other agents' work since `bef7d6b`).
